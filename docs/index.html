Overview

Relations that can be checked,
decisions that can be replayed.

Candidate plans from language models, rules, or users can be structurally well formed while missing causal support, resource ordering, or cooperative pairing. This project represents those obligations in a typed atomic task graph, then applies deterministic relation repair before scheduling.

The four stages perform state closure, synchronization pairing, resource-conflict orientation, and conservative order compression. A joint audit checks six graph conditions; strict list scheduling additionally verifies the actual execution-unit and resource occupancy. Accepted and rejected edits remain in a traceable log, while only accepted events participate in graph replay.

Controlled experiments show improved reference agreement after repair. Same-input comparisons and public evaluations also delimit the contribution: a simple comparator with the same compression is competitive on the controlled sample, and improved formal acceptance does not guarantee improved semantic agreement.

中文研究概述

本项目研究面向双执行单元协同任务的可验证原子任务图关系修复与规划层并行规划。候选由大模型、规则或用户提供；确定性后处理负责状态闭合、同步配对、资源冲突定向和保守顺序压缩。通过六项联合图审计及实际调度检查后才输出被接受计划。研究保证限于已表示的离散状态、容量1资源和执行单元占用。

01 / Method

Repair obligations in a fixed order.

Every accepted modification has a reason.
Every failed check returns a diagnostic.

  1. 01

    State closure

    Repair represented causal support with precise state labels.

  2. 02

    Sync pairing

    Pair existing support with the same source, target, and state.

  3. 03

    Resource orientation

    Turn shared-resource conflicts into an acyclic directed order.

  4. 04

    Order compression

    Trial-delete only Eorder; re-audit and accept or restore.

Six graph checksSchema-validClosedGoal-reachableAcyclicSync-completeResource-ordered

Any failed check yields diagnostics and no accepted schedule. Rejection does not prove infeasibility.

Public specifications and adaptation coverage

Six of ten AssemblyGrid recipes are fully adaptable to the represented planning model. Four recipes are excluded for unsupported cardinality or XOR semantics. One official inclusive-OR specification test is counted separately. Six OR-Library job-shop instances are projected onto two added generic execution units while retaining machine resources.

The projection is not a replication of the original robot simulation and is not compared with the original job-shop optimum. Candidates are deterministic adaptations of the frozen public specifications.

External tool candidates: acceptance is not semantic agreement

Adaptable archived candidates number 234/497 for CodeLlama-13b and 67/489 for Mistral-7b. From audit-only to the full method, accepted counts rise from 175 to 234 and 44 to 64, respectively; mean reference edge F1 falls from 0.4226 to 0.4040 and from 0.4064 to 0.3023. Tool-dependency data do not supply robot resource or cooperative-occupancy semantics.

Model-generated candidates and finite mechanism checks

The 24 GPT-6 conversation candidates contain 254 nodes. All original candidates pass, and repair produces zero net relation change. Task specifications and candidates come from the same method-aware session; these artifacts are not an independently verifiable provider API benchmark.

In a separate author-constructed three-node family, 736 of 1,728 inputs have independently checked feasible witnesses. The full method accepts 720 of them and rejects 16 feasible inputs. No false acceptance was observed in this finite family; completeness is not established.

03 / Reproduce

Run locally. Inspect every decision.

Python 3.11+ · offline evaluation
No model API or robot connection required.

One command for the frozen evaluations

Download and extract the supplementary archive. From its root, run:

python reproduce_all.py results/new_run

Use a new output directory. Stable results are checked against the archive; machine timings are not expected to match.

The current suites use only the Python standard library. Historical MILP and timing scripts have separately pinned dependencies.

Scope of the guarantee

Planning-layer verification.

The accepted interface checks represented discrete states, capacity-one resources, and L/R occupancy. It does not establish unmodelled task semantics, collision-free motion, trajectory feasibility, or hardware safety. The repair procedure is heuristic and can reject feasible inputs.
